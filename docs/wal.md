# WAL Design

## 1. Purpose

This document describes the write-ahead log model used by the matching engine prototype.

The WAL is not a generic database log. In this project it is an explicit architectural boundary between components.

The WAL provides:

* stable ordering of commands;
* durable record of accepted input;
* durable record of produced execution events;
* replayability;
* auditability;
* deterministic recovery tests;
* separation between matching logic and downstream consumers.

The first prototype keeps the WAL intentionally simple. The design should be easy to inspect, test, and replace with a more efficient implementation later.

---

## 2. Core Idea

The matching engine is modelled as a deterministic transformation:

```text
Command WAL -> Matching Rules -> Execution Event WAL
```

Commands are normalized input requests.

Execution events are durable facts produced by the matcher.

Given the same command sequence and the same matching rules, the matcher must produce the same execution event sequence.

The WAL makes this property testable.

---

## 3. Log Types

The full architecture may use multiple logs:

```text
Trading Ingress WAL
Instrument Command WAL
Execution Event WAL
```

The first prototype uses two logical logs:

```text
Command WAL
Execution Event WAL
```

This is enough to demonstrate the core model.

## 3.1 Command WAL

The Command WAL stores normalized commands accepted for processing.

It answers the question:

```text
What did the system accept as input, and in what order?
```

The Command WAL is the primary input for replay.

## 3.2 Execution Event WAL

The Execution Event WAL stores events generated by the matcher.

It answers the question:

```text
What facts did the matching engine produce?
```

This log can be consumed by:

* market data builders;
* trade reports;
* database mirrors;
* audit tools;
* replay validators;
* test tools.

---

## 4. Command Log vs Event Log

Commands and events are intentionally separated.

A command is a request:

```text
Client wants to place, cancel, or replace an order.
```

An event is a fact:

```text
The engine accepted an order, rejected it, executed a trade, cancelled an order, or modified book state.
```

This distinction matters.

A command may produce:

* no event;
* one event;
* multiple events.

For example, a single aggressive order may match several resting orders and produce several trade events.

---

## 5. Ordering Model

Each WAL record has a monotonically increasing sequence number.

For the first prototype:

```text
Command sequence is local to the Command WAL.
Event sequence is local to the Execution Event WAL.
```

Each execution event also stores the command sequence that caused it.

This gives the relationship:

```text
Command sequence N -> one or more execution events referencing N
```

Example:

```text
Command #1001: New buy order
Event #5001: OrderAccepted, command #1001
Event #5002: TradeExecuted, command #1001
Event #5003: TradeExecuted, command #1001
Event #5004: OrderFullyFilled, command #1001
```

The prototype does not require globally synchronized sequence numbers across all logs.

---

## 6. Minimal Record Model

Every WAL record should contain enough metadata to be read, validated, and replayed.

A conceptual record layout:

```text
record_length
record_type
sequence_number
payload_length
payload
checksum
```

For a binary implementation:

```text
+------------------+
| magic            |
| version          |
| record_length    |
| record_type      |
| sequence_number  |
| payload_length   |
| payload          |
| checksum         |
+------------------+
```

For the first prototype, a simpler text-based format is acceptable if the same semantics are preserved.

---

## 7. Prototype Format

The first implementation may use JSON Lines.

One record per line:

```json
{"seq":1,"type":"NewOrder","instrument":"EURUSD","order_id":100,"side":"Buy","price":10125,"qty":10}
{"seq":2,"type":"NewOrder","instrument":"EURUSD","order_id":101,"side":"Sell","price":10120,"qty":4}
```

For execution events:

```json
{"seq":1,"cmd_seq":1,"type":"OrderAccepted","instrument":"EURUSD","order_id":100,"price":10125,"qty":10}
{"seq":2,"cmd_seq":2,"type":"TradeExecuted","instrument":"EURUSD","order_id":101,"contra_order_id":100,"price":10125,"qty":4,"trade_id":1}
{"seq":3,"cmd_seq":2,"type":"OrderFullyFilled","instrument":"EURUSD","order_id":101}
{"seq":4,"cmd_seq":2,"type":"OrderPartiallyFilled","instrument":"EURUSD","order_id":100,"remaining_qty":6}
```

JSONL is not the target production format. It is useful because it is easy to inspect, diff, generate, and test.

A later implementation may replace it with a fixed binary format.

---

## 8. Binary Format Direction

A later binary WAL format may use:

```text
file header
fixed-size record header
payload
crc32 or crc64
padding / alignment
```

Possible file header:

```cpp
struct WalFileHeader
{
    uint32_t magic;
    uint16_t version;
    uint16_t header_size;
    uint32_t record_header_size;
    uint32_t flags;
};
```

Possible record header:

```cpp
struct WalRecordHeader
{
    uint32_t record_length;
    uint16_t record_type;
    uint16_t header_size;
    uint64_t sequence_number;
    uint32_t payload_length;
    uint32_t payload_crc;
};
```

This is not required for the first prototype.

The first prototype should define interfaces in a way that allows changing the physical WAL format without changing the matcher.

---

## 9. WAL Writer Interface

The matcher should not depend on a concrete file format.

A minimal writer interface:

```cpp
class IWalWriter
{
public:
    virtual ~IWalWriter() = default;

    virtual uint64_t append(std::span<const std::byte> payload) = 0;
    virtual void flush() = 0;
};
```

A typed wrapper may exist above this interface:

```cpp
class ExecutionEventLog
{
public:
    uint64_t append_event(const ExecutionEvent& event);
    void flush();
};
```

The matcher should call a narrow event output interface, not perform file operations directly.

---

## 10. WAL Reader Interface

Replay uses a reader interface.

```cpp
class IWalReader
{
public:
    virtual ~IWalReader() = default;

    virtual bool read_next(WalRecord& record) = 0;
};
```

A typed command reader may exist above it:

```cpp
class CommandLogReader
{
public:
    bool read_next_command(OrderCommand& command);
};
```

This keeps parsing and matching separate.

---

## 11. Append Semantics

A WAL append operation should be atomic at the record level from the logical point of view.

For the prototype:

```text
append(record) either succeeds and returns a sequence number,
or fails and does not advance the sequence.
```

Physical guarantees may be weaker in the first file-based implementation, but the interface must make the intended semantics clear.

A failed partial write must be detectable during recovery or replay.

---

## 12. Flush Semantics

The prototype separates append from flush.

```text
append -> writes record to the log abstraction
flush  -> forces buffered data to the underlying storage layer
```

The first implementation may use ordinary file flushing.

A later implementation may distinguish:

```text
buffer flush
OS flush
fsync
replicated commit
```

Those concerns are outside the first prototype.

The important architectural point is that durability policy is outside the matcher.

---

## 13. Record Integrity

A WAL reader must be able to detect incomplete or corrupted records.

Minimum checks:

```text
record length is valid
record type is known
sequence number is expected or acceptable
payload length matches record length
checksum matches payload
```

In JSONL prototype mode, checksum may be omitted initially, but malformed records must still be rejected.

A later binary implementation should include checksum per record.

---

## 14. Recovery Rules

During recovery, the WAL reader processes records sequentially.

If an incomplete trailing record is found, recovery may stop at the last valid record.

Example:

```text
record 1: valid
record 2: valid
record 3: valid
record 4: incomplete trailing record
```

Recovery result:

```text
records 1..3 are accepted
record 4 is ignored or reported as incomplete
```

Corruption in the middle of the log is a stronger error and should not be silently ignored.

---

## 15. Replay Procedure

Replay from the Command WAL:

```text
1. Create an empty order book.
2. Open the Command WAL.
3. Read commands in sequence order.
4. Apply each command to the matcher.
5. Generate execution events.
6. Compare generated events with the stored Execution Event WAL.
```

The replay correctness condition:

```text
same command sequence + same matching rules = same execution event sequence
```

Replay validates determinism.

It also helps detect:

* corrupted logs;
* accidental non-determinism;
* changed matching rules;
* invalid checkpoints;
* implementation regressions.

---

## 16. Event Comparison

Replay comparison should not be based on formatted strings.

It should compare normalized event fields.

Important fields:

```text
event type
command sequence
instrument id
order id
contra order id
price
quantity
trade id
remaining quantity
event order
```

If timestamps are added later, they must be handled carefully.

Wall-clock timestamps should not affect deterministic replay unless they are part of the input command stream.

---

## 17. Time Handling

The matcher must not call wall-clock time to decide matching behavior.

If time is needed, it must be part of the command input.

Acceptable:

```text
command.accepted_timestamp is assigned before the command enters the Command WAL
```

Not acceptable inside matcher:

```text
now() is called during matching and affects event order or event content
```

This rule protects deterministic replay.

---

## 18. File Rotation

File rotation is not required for the first prototype.

A later version may rotate logs by:

```text
size
time
instrument
sequence range
session
```

If rotation is introduced, the log metadata must preserve sequence continuity.

Example:

```text
command_000001_000100.wal
command_000101_000200.wal
command_000201_000300.wal
```

The replay reader must treat rotated files as one logical sequence.

---

## 19. Checkpoints and WAL

Checkpoints are optional optimization.

The WAL remains the source of truth.

A checkpoint must include:

```text
instrument id
last applied command sequence
order book snapshot
snapshot version
checksum or validation metadata
```

Recovery from checkpoint:

```text
1. Load checkpoint.
2. Verify checkpoint metadata.
3. Open Command WAL.
4. Seek to command after last_applied_command_sequence.
5. Replay remaining commands.
```

A checkpoint must never make earlier command records semantically irrelevant. It only reduces recovery time.

---

## 20. Multiple Instruments

The first prototype may use one Command WAL for all instruments.

Later options:

```text
single global Command WAL
per-instrument Command WAL
global ingress WAL + per-instrument command WALs
```

Trade-offs:

## 20.1 Single Global Command WAL

Advantages:

* simple total ordering;
* easier audit of accepted input;
* easier prototype implementation.

Disadvantages:

* matcher workers need filtering or dispatching;
* high-volume instruments share one log;
* replay by instrument may require scanning unrelated records.

## 20.2 Per-Instrument Command WAL

Advantages:

* natural ownership by matcher;
* easier per-instrument replay;
* simpler parallel processing.

Disadvantages:

* requires dispatcher;
* cross-instrument ordering is more complex;
* global audit requires joining streams.

## 20.3 Ingress WAL + Per-Instrument WAL

Advantages:

* preserves external acceptance history;
* gives each matcher a clean per-instrument stream;
* closer to production architecture.

Disadvantages:

* more moving parts;
* requires source references between logs;
* more complex recovery model.

For the first prototype, either single global Command WAL or direct per-instrument Command WAL is acceptable.

The preferred architecture direction is:

```text
Trading Ingress WAL -> Per-Instrument Command WAL -> Execution Event WAL
```

---

## 21. Source References

When multiple logs exist, records should reference their source records.

Example:

```text
Ingress record #9001
        |
        v
Instrument command record #120
        |
        v
Execution event records #501, #502, #503
```

This allows tracing:

```text
external request -> normalized command -> execution events
```

For the first prototype:

```text
source_record_id
command_sequence
event_sequence
```

are enough.

---

## 22. Error Handling

The WAL layer should report explicit errors.

Examples:

```text
Cannot open log file
Cannot write record
Flush failed
Invalid record length
Unknown record type
Checksum mismatch
Unexpected sequence number
Malformed payload
Incomplete trailing record
```

The matcher should not hide WAL write failures.

If an execution event cannot be persisted according to the configured durability policy, the engine must not pretend that the command was successfully processed.

For the first prototype, fail-fast behavior is acceptable.

---

## 23. Durability Policy

The prototype should keep durability policy explicit but simple.

Possible policies:

```text
NoSync      - useful only for tests and demos
Flush       - flush language/runtime buffers
Fsync       - request OS-level durability
Replicated  - out of scope for prototype
```

The matcher should not hard-code a durability policy.

Durability belongs to infrastructure configuration.

---

## 24. Idempotence and Duplicate Detection

The first prototype may assume command sequences are unique and ordered.

Later versions should handle duplicate command delivery.

Possible duplicate keys:

```text
client id + client order id
source record id
command sequence
```

Duplicate handling must be deterministic.

A duplicated command should not create duplicated trades.

---

## 25. WAL and Matcher Boundary

The matcher consumes commands and produces events.

It must not know:

* file names;
* file offsets;
* physical WAL format;
* fsync policy;
* rotation policy;
* replication policy.

It may know:

* command sequence;
* command content;
* event sequence assigned by output event writer;
* whether event persistence succeeded or failed.

This keeps the matching core testable.

---

## 26. Suggested Prototype Steps

### Step 1: In-Memory Log

Implement an in-memory command log and event log.

Purpose:

```text
unit tests
matching rules
event ordering
replay without file I/O
```

### Step 2: JSONL File Log

Implement a simple file-backed JSONL log.

Purpose:

```text
manual inspection
example sessions
replay from disk
demo-friendly output
```

### Step 3: Binary Log

Introduce binary record layout only after the model is stable.

Purpose:

```text
performance
record integrity
explicit checksums
better recovery behavior
```

Do not start with binary WAL unless the domain model and replay tests are already stable.

---

## 27. Minimal Acceptance Criteria

The WAL layer is acceptable for the first prototype when:

```text
Commands can be appended in sequence.
Events can be appended in sequence.
Commands can be read back in the same order.
Events can be read back in the same order.
Replay from Command WAL produces the same normalized event sequence.
Malformed input is detected.
Incomplete trailing records do not corrupt valid previous records.
The matcher does not depend on the concrete WAL implementation.
```

---

## 28. Summary

The WAL is the backbone of the prototype.

It is used not only for persistence, but also for ordering, auditability, replay, and deterministic validation.

The most important design rule is:

```text
The matcher is deterministic.
The WAL preserves the input and output sequences.
Replay proves that the same input produces the same output.
```

The first implementation should be simple, inspectable, and replaceable.

A simple WAL that supports deterministic tests is more valuable than a complex binary log without a stable domain model.
