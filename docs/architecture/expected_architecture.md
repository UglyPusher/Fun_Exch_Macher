## Expected WAL Boundary

The WAL boundary is binary and write-ack driven. A record or batch becomes visible to the next stage only after the disk writer confirms the write/flush.

```text
[Command WAL API] ---> [Pending Records / Batch]   [implemented in writer state]
                           |
                           v
                      [Disk Writer]                [implemented as binary segment writer]
                           |
                      write/flush/fsync ack        [implemented in WAL-v0 facade]
                           |
                           v
                    [Committed Visibility]         [implemented in WAL-v0 facade]
                           |
                           v
                    [Command Reader]               [implemented as raw/typed segment reader]
```

Analogous target event path:

```text
[Event WAL API] ---> [Pending Records / Batch]     [implemented behind facade]
                         |
                         v
                    [Disk Writer]                  [implemented as binary segment writer]
                         |
                    write/flush/fsync ack          [implemented in WAL-v0 facade]
                         |
                         v
                  [Committed Event Visibility]     [implemented in WAL-v0 facade]
```

The current WAL implementation is strict and binary: segment files, segment headers, record headers, payload CRC32, sequence validation, internal raw readers/writers, typed adapters, recovery scanning, and committed visibility after successful facade append.

## Sources Of Truth

```text

Execution Event WAL     source of deterministic execution facts
Snapshots               planned recovery accelerator, not implemented yet

```

## First Prototype Cut

The first meaningful prototype should focus on this narrower slice:

```text
Command WAL
    -> Single-instrument deterministic matcher
    -> OrderBook FSM
    -> Execution Event WAL
    -> Replay validation
```

This slice is now implemented for `NewOrder`, `CancelOrder`, and `ReplaceOrder`, including validation replay. Risk, reservation, portfolio, accounting, and market-data blocks remain visible in the target design as integration points, but they should stay as stubs until the matching/replay core grows beyond the first command set.
